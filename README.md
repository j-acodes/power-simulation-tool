# Power Simulation Tool

A tool to size PV, BESS, and hybrid plants, backed by catalogues of component parameters
(cables, transformers, inverters, and BESS products).

The core idea: the electrical chain from the **Point of Connection (POC)** back to the
**inverter** is walked as a *loss cascade*, accumulating active and reactive losses, to
find the power the inverters must actually deliver.

```
POC ── HV transformer ── MV cables ── MV transformer ── AC cables ── inverter/PCS ── (cell)
```

## Status

**Core engine (done)** — component physics models (`powertool/components.py`) + YAML
databases (`data/`), chain assembly and database loader (`powertool/chain.py`,
`powertool/database.py`), the backward-sweep solver (`powertool/sizing.py`), plant
architecture (`powertool/architecture.py`) and the PDF report
(`powertool/pdf_report.py`).

**Diagram builder (implemented)** — a FastAPI backend (`backend/`) and a React canvas
(`frontend/`) where a plant is drawn block by block and solved live: projects and
designs persisted with optimistic locking, a seed wizard that proposes a plant from a
POC target, auto-arrange, full result tables and a PDF report download. See
**Running the app** below.

PV stations explicitly select a catalogue or custom inverter and an integer count. Installed
inverter power at the design ambient governs PV station count, duty allocation, and active /
apparent conversion warnings; transformer-station loading remains a separate check. An inverter
is contained by a station and is never a standalone canvas node. See
[ADR-0005](docs/adr/0005-inverter-power-governs-pv-conversion.md).

**Removed** — the original Streamlit UI (`app/streamlit_app.py`) and the Markdown
report and Graphviz diagram it alone consumed (`powertool/report.py`,
`powertool/diagram.py`). The diagram builder replaced it and the engine is now tested
directly. Read it at `b5fc748` if you need the provenance of a ported constant.

```bash
python examples/pv_sizing_example.py     # command-line example
```

**Cable auto-sizing:** cable sections are not picked by hand. You give each cable
section its voltage, length (in metres), and zone; the tool sets the number of
parallel circuits from ampacity (current ≤ a max utilisation, default 80%) and then
picks the **smallest cross-section** that keeps the cable's active loss within an
admissible **power-loss budget** (per section, as % of the local active power):

- **Collection** cables (inverters → MV/HV transformer): default **1.30 %**.
- **Export** cables (last MV panel → POC): default **0.10 %/km** × length.

Voltage drop is available as an optional extra cap but is off by default — the loss
budget governs.

**Cable catalogue** (`data/cables.yaml`, generated by `data/build_cable_catalogue.py`):
aluminium XLPE, LV 0.6/1 kV and MV 12/20 / 18/30 / 20/35 kV (up to 40.5 kV Um), sizes
to 630 mm² (the practical max for PV MV switchgear terminations). Resistance is AC at
90 °C from IEC 60228; reactance, ampacity (buried) and charging are representative —
**validate against your supplier datasheets and installation conditions.** Edit the
source values in `build_cable_catalogue.py` and re-run to regenerate.

The current implementation and historical ticket status are tracked in
[`docs/project-status.md`](docs/project-status.md). Vocabulary and durable design
decisions live in [`CONTEXT.md`](CONTEXT.md) and [`docs/adr/`](docs/adr/); the original
acceptance criteria and implementation evidence remain in [`.scratch/`](.scratch/).

## Modelling assumptions

Three-phase, balanced, positive-sequence, RMS, steady-state. Voltages are line-to-line
in kV; P in kW, Q in kvar, S in kVA.

## Running the app

The diagram builder is one FastAPI process: it serves the `/api` routes and, when
`frontend/dist` exists, the built React app alongside them.

### Docker

```bash
docker build -t powertool .
docker run -p 8000:8000 -e DATABASE_URL="postgresql+psycopg://user:password@host:5432/powertool" powertool
```

Then open <http://localhost:8000>. Projects and designs live in the Postgres database
`DATABASE_URL` names, so they survive the container. The image builds the frontend
with Node in a first stage and ships only Python — see `Dockerfile`.

### Locally

Work inside a virtualenv, so `python3`, `pytest` and `uvicorn` all resolve to this
project's Python (3.12, matching the Docker image) rather than whatever is on your
PATH. You also need a Postgres server with a database for the app (any recent
version; the official installer is enough) and `DATABASE_URL` pointing at it — see
[Configuration](#configuration). Install the dependencies once, then use the root
development command:

```bash
python3.12 -m venv .venv          # once
source .venv/bin/activate         # every new shell
pip install -r requirements.txt
npm ci --prefix frontend
npm run build --prefix frontend
npm run dev                            # http://localhost:5173
```

The root `npm run dev` starts Vite and supervises the FastAPI backend with reload,
proxying `/api` to port 8000. If a backend is already listening there, the supervisor
stands down and Vite proxies to that process.

### Configuration

| Variable | Default | Notes |
| --- | --- | --- |
| `DATABASE_URL` | none — required | Postgres URL, e.g. `postgresql+psycopg://user:password@host:5432/powertool`. Add `?sslmode=require` for a managed server. The app refuses to start without it. |
| `TEST_DATABASE_URL` | none — tests only | A disposable Postgres database whose name ends in `_test`. See [Tests](#tests). |

Keep the password out of the repository: set the variable in the environment or the
deployment's secret store.

### Database migrations

The schema is owned by Alembic migrations in `backend/migrations/versions/`. The app
applies any pending migration itself at startup, so deploying new code is enough to
bring the database up to date; nothing is ever dropped to change the schema. The
database user therefore needs permission to create and alter tables in its database.

After changing a model in `backend/models.py`, write the matching migration and review
it before committing (`tests/test_persistence.py` fails while models and migrations
differ):

```bash
alembic revision --autogenerate -m "add designs.foo"   # against DATABASE_URL
```

`alembic downgrade -1` steps back one migration; on a database that holds real
projects, back it up first. Diagrams saved under an older stored contract, such as one
saved before PV inverter selection became required, are not inferred or upgraded.

## Tests

The tests need their own Postgres database. Each run drops every table in it, so the
test setup refuses any database whose name does not end in `_test`:

```bash
export TEST_DATABASE_URL="postgresql+psycopg://user:password@localhost:5432/powertool_test"
.venv/bin/python -m pytest -q             # engine, API, graph, and seed tests
DATABASE_URL="$TEST_DATABASE_URL" npm --prefix frontend test
npm --prefix frontend run build            # TypeScript check + production build
npm --prefix frontend run lint             # oxlint
```

Vite can start a backend during frontend tests. Pointing `DATABASE_URL` at the test
database isolates any backend started by this command from real data.
